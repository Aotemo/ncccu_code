# F05 最终选员 CPU 准备

范围仅为 `tools/diagnostics/f05_final_selection.py`、`tests/test_f05_final_selection.py` 和本说明。复用 F03 的完整同 population 轮次发现与公开源门、F04 的独立进程严格构造/完整推理状态导出与实际文件 SHA/字节、固定体积贪心和内部 dev z 等权函数；三汤沿既有 `f05_soup_dev.py` 检查实际父源、单独加载及已完成的八 rank 全 dev 分片。此处不派 GPU、不读官方，样本级预测不进入 Git。

在全部授权方向终态及任何新的 F05 融合结果读取前，由 owner 从 F03 发现结果和三汤／新模型补充清单建立完整候选，按事前固定顺序封存。当前候选与最终规则尚未封存；下面的 policy 格式只是可测试的接线草案，不宣称已有正式 F05 清单。清洗/蒸馏候选在其真实完成后才来自同一轮次发现，非完整或缺 selected 的条目列为 unknown。R256 在 F04 的历史排除仍保留；它已获准作为 F05 汤父模型，能否作为 F05 独立候选以未来完整封存规则为准，不在此猜测。

`screen_candidates` 对每个达到单模 `AUROC >= 0.988` 的轮次使用 `f04_export_member.py` 的实际严格构造/重载回执，并重新核 checkpoint、sidecar、freeze、science、两精度文件 SHA/实际字节及 online/EMA 身份。已有导出若绑定较早库存，须实读旧库存并按 F04 `require_same_candidate` 核该成员与现库存所有身份完全相同，不能把旧库存 SHA 写作新库存 SHA。历史任务内 fit 适配成员还须绑定现有适配审计与该轮真实阶段回执；证据缺失列 unknown。每个均匀汤使用原真实父模型 SCIENCE、来源、已有 strict standalone/export，以及完整内部 dev producer 输入和 rank packet。F03 已完成枚举且 `selected_checkpoint_missing`、候选为空并含完整 selected 身份时列为已知不可部署的排除；枚举失败、多候选、缺加载回执或来源不明列 unknown，低于门槛列排除；N06/FLAIR 不准入。未解决的 unknown 会阻止当前 helper 函数生成最终预封存，不能静默跳过并把剩余集合声称完整。

`freeze_selection` 接受外部真实封存的 `f05-final-selection-policy-v1`：绑定完整候选顺序、F03 inventory 和 soup catalog 两项 SHA、全部授权方向的终态小回执、`.988` 门、单模 AUROC 降序/同分按封存顺序、`500000000` 实际 fp16 字节、遇到下一成员超限立即停止、内部 dev float64 总体标准差 z 等权、`TTA=false`、`official_read=false` 和未读新融合。该 policy 结构须经 08ac 审阅并与正式终态回执约定后才能用于正式选择；不是根据现有结果预先产生的最终合同。当前汤验真适配已登记的三组均匀汤；若次方案贪心汤或其他新汤真实存在，须先补充其来源与验真适配，未知项不得静默遗漏。

候选筛查命令显式输入 SHA 固定的 `--inventory`、`--soup-catalog`、`--policy`、`--evidence`、当前 Pod 完整树 `--source-proof`、`--remote-metadata`、`--git-commit`、`--work-root`、新 `--output`；缺失项保留 `SCREEN.json` 并拒绝生成 `PREFLIGHT.json`。现有 F04 全 dev 的原 fp16 分片未逐文件 SHA 绑定，不能将其事后散片冒充已封存的最终预测。正式融合须在选员预封存 SHA 后，由唯一 GPU owner 使用现有监督链取得每个选中成员固定 fp16 存储的完整内部 dev 单视图分片，核 checkpoint/导出、成员、顺序、行与 rank proof，再复用 `fuse_internal_dev` 的 F04 z 等权与 AUROC/AP。最终 producer 的预测封存和调用入口尚需 08ac 接线，不能把纯函数合成结果当正式 F05 dev 指标。官方评估仍只有最终冻结后的独立 F05 一次 claim。

候选补充文件草案为 `{format:'f05-soup-candidates-v1', official_read:false, soups:[{id:'soup-r120'}, {id:'soup-r134r1'}, {id:'soup-r201'}]}`；未来若增加其他已完成汤，须在其 adapter 和来源核验完成后、政策封存前扩充。私有证据文件 `{format:'f05-candidate-evidence-v1', official_read:false, entries:{...}}` 按候选 ID 指向轮次 F04 `EXPORT.json` 的 `{path,sha256}` 或汤的 `{inputs:{path,sha256},summary:{path,sha256}}`；轮次如果复用旧库存导出，改为 `{export:{path,sha256},original_inventory:{path,sha256}}`，如涉及 fit 适配再提供 `adaptation_audit` 与 `adaptation_receipt`。各路径由真实证据确定，不将占位 ID 或虚构 SHA 作为正式输入。

**三折候选发现缺口及裁定：** F03 旧发现逻辑只接受 freeze 所指 manifest 等于原始 SHA，直接跳过使用派生训练 manifest 的 R265–R267；因此它的现有输出不能单独视为 F05 完整候选。c607 已裁定这三轮必须纳入发现，不能特殊排除；08ac 负责扩展现有发现入口。选员命令先要求三轮均有显式发现行，缺任何一轮即停止。合法三折行沿用 `science`、`spec.freeze/completion`、`selected` 和 checkpoint 字段，另附 `fold_binding={fold,site,runtime_binding,training_manifest}`，其中三项文件均以 `{path,sha256}` 固定。选员对 round SCIENCE 与 site 所指 SCIENCE 分别读 SHA 并核一致，复用 `verify_bound_fold` 核原数据与三折 seal、派生 freeze/manifest，核实际训练 manifest SHA 和原 dev 的完整索引及行；实际结构或任一身份不符记 unknown。其他非登记 manifest 仅核同轮完成 freeze 的实际字节及其声明的 manifest SHA，并与原始和三折登记 SHA 比对；明确记 `freeze_declared_training_manifest_mismatch`，不读取或要求不相关 manifest 文件；未识别的发现状态、发现失败或三折 binding 缺失不能当作排除。最终 fp32 原预测也须先通过这些折绑定，再按派生 manifest 校验 selected/precision，和原 dev 同序比较。合成检查已通过；当前接口仍待 08ac 发现代码合入后的精确集成。

policy `direction_terminals` 必须恰含 `soup`、`oof`、`clean`、`distill`、`resolution_768` 五个 `{path,sha256}`；每项的真实终态汇总须标明对应 `direction`、`status` 为 `completed` 或 `closed_no_candidate`、`official_read=false`。这一结构只是接口提案，须与该时实际终态/归档回执协调；任一方向 unknown 时不能编造终态或冻结。

## 选中成员 dev 分片的接线草案

以下 reducer 已通过 Pod 合成验证；不是已发布的生产接口，也不授权真实选员、推理或融合。计划由 08ac 在现有 `f04_gpu_full_dev.py` 的 owner/worker 监督链接入，先审阅最终候选和 policy，再封选员、准备各成员独立严格加载资产，最后由 owner 产生并封存分片；不新增训练或 GPU 平台。八个 rank 可以分多次覆盖全部选中成员，但每个成员在整组 seal 中恰出现一次。

每批 `{path,sha256}` 固定的 `f05-selected-dev-packets-v1` 小回执包括：`status='selected_fp16_dev_completed'`、`preflight_sha256`、`manifest_sha256`、`inputs`、`worker_spec`、`release`、`source_tree_proof`，按物理 rank 0–7 的 `proofs` 和 `packets` 八个文件引用，及 `forward_counts={成员id:内部dev行数}`、`storage='fp16'`、`arithmetic='fp32'`、`TTA=false`、`official_read=false`。其中 `inputs` 使用 `f05-selected-dev-inputs-v1`，绑定相同 `preflight_sha256` 和原始 `manifest={path,sha256}`，明确 `batch_size=8`、`view='identity'`、`model_mode='eval'`、`dev_count`、`dev_positive`、`TTA=false`、`official_read=false`，并含八项 `plan` 和成员列表。每个成员沿现有 worker 所需结构提供 `round_id`、`selected.variant`、`model`、`metadata` 及原有运行依赖，另附与选员预封存一致的 `id`；普通成员 `id=round_id`，汤的 `id='soup-'+round_id`。`model` 绑定 fp16 文件 SHA、实际字节和 fp16 tensor SHA，`metadata` 绑定同一 SHA、tensor 和 variant。`plan.member` 取 worker 的 `round_id`，`forward_counts` 的键取最终候选 `id`。

`worker_spec.inputs`、八 rank 设备证明及其 `release` 与每个 packet 的 input/proof SHA 必须相互绑定；每包保留现有原始 index/name/label/logit/probability 与 batch/offset/rank 字段。正常模式每 rank 在设备证明屏障后由现有 worker 严格加载固定资产并验证来源，不使用官方模式或汤的双精度研究模式。真实封存必须在当前完整源码证明、发布 Git commit 和 producer worker 文件 SHA 一致时才被消费；单凭 producer 自报 SHA 不够。此处的 schema 是供 owner 审阅的接线提案，旧 F04 packet 或仅有汇总 SHA 的旧产物不能直接套用。

草拟的 `fuse` 子命令只做 CPU 归约：显式给 `--preflight`、`--screen`、`--policy`、`--manifest`、可重复的 `--packet-seal`、`--source-proof` 的路径与 SHA，并指定 `--remote-metadata`、`--git-commit`、`--work-root`、全新 `--output`。它重算预封存规则、逐文件核指纹和完整行覆盖，使用固定的 float64 总体 z 等权。每个原 selected 的 fp32 对照通过现有 `paired_evidence` 独立核 sealed manifest、selected variant/update/tensor、预测与 precision 文件 SHA 和逐行顺序；均匀汤的 fp32 对照只取其受监督 producer 的对应 packet 和逐文件 SHA，重新核父源、模型、输入、设备 proof、覆盖与汤汇总。各成员的 fp32/fp16 AUROC、AP、最大 logit 与 z 差及相同成员整体融合对照均应保留；任一来源或完整性不明即拒绝归约。输出只含聚合指标、矩、身份及 SHA，不将逐样本分数写入 Git。实际调用仍需同一发布源码的 Pod 全树证明、合成测试、owner producer 和已固定正式候选；尚未支持或尚无可信旧预测的成员必须由 owner 先解决，不能作为已通过。
